# C43. 错误与调试

## 节点定位

- 所属模块：文件、调试与综合应用
- 学习难度：综合应用
- 建议学习时间：120-150 分钟
- 典型用途：根据可重复证据定位程序问题，修正根本原因并验证没有引入新错误。

## 学习目标

- 区分预处理、编译、链接、运行时、逻辑和输入数据错误。
- 能从第一条关键诊断信息开始定位问题。
- 会启用常用警告并理解“警告不等于可以忽略”。
- 掌握复现、缩小范围、提出假设、验证和回归测试的调试流程。
- 会使用调试输出、断言和调试器观察程序状态。
- 了解运行时检查工具对越界和无效指针问题的帮助。
- 能设计正常、边界和错误测试用例。

## 一、调试不是反复猜测

调试是寻找程序实际行为与预期行为产生差异的原因。有效调试依赖证据：

```text
明确预期 -> 稳定复现 -> 找到首次偏离 -> 提出原因假设 -> 用实验验证 -> 修复 -> 回归测试
```

如果一次修改许多位置，再观察程序是否“好像正常”，即使问题消失，也很难确认真正原因。一次只验证一个清楚假设，更容易建立可靠结论。

## 二、错误的主要类型

### 1. 预处理错误

例如找不到头文件、条件编译未配对或宏展开产生异常文本：

```text
fatal error: student.h: No such file or directory
```

应检查文件名、包含路径、头文件保护和宏定义。

### 2. 编译错误

源代码不符合 C 语法或类型规则：

```c
int value = ;
```

常见原因包括遗漏分号、括号不配对、名称未声明和参数类型不一致。

### 3. 链接错误

每个源文件可能已经编译成功，但组合时找不到定义或发现重复定义：

```text
undefined reference to `calculate_average`
multiple definition of `student_count`
```

应检查实现文件是否加入编译命令，以及普通函数或全局变量是否定义了多次。

### 4. 运行时错误

程序启动后崩溃、卡住、异常退出或访问非法资源。例如空指针解引用、数组越界和无限循环。

### 5. 逻辑错误

程序能够运行，但结果不符合需求。例如平均值计算使用了错误分母，循环漏掉最后一个元素，或边界条件写错。

### 6. 输入与外部资源错误

用户输入格式不正确、文件不存在或数据记录损坏，并不一定是程序缺陷。程序缺陷可能在于没有正确检测和报告这些正常可预见的失败。

## 三、先判断错误发生在哪个阶段

面对问题时先问：

1. 预处理是否成功？
2. 每个源文件是否编译成功？
3. 链接是否成功？
4. 程序是否启动？
5. 程序在哪个输入和步骤出现偏差？

阶段不同，调查方向也不同。链接器提示找不到函数定义时，继续修改函数内部算法通常没有帮助；逻辑结果错误时，反复调整头文件搜索路径也没有帮助。

## 四、认真处理编译器警告

建议在学习阶段启用常用警告：

```text
gcc main.c -std=c11 -Wall -Wextra -Wpedantic -o main
```

警告可能指出：

- 格式说明符与参数类型不匹配；
- 变量可能未初始化；
- 函数声明和调用不一致；
- 有符号与无符号比较可疑；
- 条件表达式中的赋值可能是笔误；
- 声明了但未使用的变量或函数。

警告不一定都代表程序必然错误，但每一条都应理解原因后再决定如何处理。不要通过随意强制类型转换或删除代码来隐藏警告。

## 五、优先阅读第一条关键错误

一个缺失的右花括号可能让编译器在后面几十行连续报告错误。后续错误常是第一处语法破坏的连锁反应。

建议顺序：

1. 找到最前面的错误或警告；
2. 阅读文件名、行号和消息；
3. 同时检查该行之前的分号、括号、引号和声明；
4. 修正一处后重新编译；
5. 再处理仍然存在的下一条诊断。

诊断行号是编译器发现问题的位置，不一定是问题真正开始的位置。

## 六、建立稳定复现

在调试前记录能够触发问题的条件：

- 使用哪个可执行版本；
- 输入了什么数据；
- 从哪个目录运行；
- 使用了哪些文件；
- 预期结果是什么；
- 实际结果或错误消息是什么；
- 问题是否每次发生。

例如，“程序有时算错”很难调查；“输入 3 个成绩 80、90、100 时平均值输出 67”则提供了明确复现。

## 七、寻找第一次偏离预期的位置

不要只盯着最终错误输出。应从输入到输出逐步检查中间状态：

```text
输入是否正确读入？
数组中的元素是否正确？
循环次数是否正确？
累计和从哪一步开始不对？
输出格式是否只是显示问题？
```

根本原因通常位于“第一次错误状态”附近，而不是最终表现的位置。

## 八、使用调试输出

```c
fprintf(stderr, "debug: i=%d, sum=%d, score=%d\n",
        i, sum, scores[i]);
```

有效的调试输出应包含：

- 当前执行位置或阶段；
- 关键变量名称和值；
- 循环下标或记录编号；
- 必要时包含文件名和行号。

不要只输出 `here` 或一个数字，因为多处输出混合后难以判断来源。

调试输出使用完毕后应删除，或纳入可控制的日志机制，避免正式程序被临时信息淹没。

## 九、用小输入手工推演

若求和循环错误，先使用 3 个容易计算的数字：

```text
数据：10, 20, 30
预期累计：10 -> 30 -> 60
```

逐轮记录：

| 轮次 | i | 当前元素 | sum 执行前 | sum 执行后 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0 | 10 | 0 | 10 |
| 2 | 1 | 20 | 10 | 30 |
| 3 | 2 | 30 | 30 | 60 |

小输入能降低观察复杂度，也便于发现循环边界、初始化和更新顺序问题。

## 十、缩小问题范围

可以逐步排除模块：

- 暂时使用固定数组替代文件输入；
- 单独调用一个计算函数；
- 删除与问题无关的界面代码；
- 把长函数拆成可分别验证的小函数；
- 在数据进入和离开模块时打印摘要。

如果固定数据计算正确，而从文件读取后错误，调查重点就从算法转向文件解析。

## 十一、构造最小复现

最小复现是保留能够触发问题的最少代码和数据。它有助于：

- 排除无关因素；
- 更快重复测试；
- 看清类型和生命周期；
- 向教师或同学准确说明问题。

缩减时每删除一部分都重新运行，确保问题仍然存在。不要一次删掉大量代码后得到另一个完全不同的问题。

## 十二、使用 assert 检查程序内部条件

`assert` 声明在 `<assert.h>` 中：

```c
#include <assert.h>

double average(const int scores[], int count) {
    assert(scores != NULL);
    assert(count > 0);

    int sum = 0;
    for (int i = 0; i < count; i++) {
        sum += scores[i];
    }
    return (double)sum / count;
}
```

断言条件为假时，程序通常输出位置并终止，帮助发现程序内部约定被破坏。

断言适合检查“按照程序设计本来必须成立”的条件，不适合处理用户输错、文件不存在等可预见情况。定义 `NDEBUG` 后，标准断言可能被关闭，因此断言表达式中不能放必须执行的赋值或函数调用。

## 十三、使用调试器

调试器可以暂停程序、逐行执行并观察变量。使用 GCC 时通常先加入调试信息：

```text
gcc main.c -std=c11 -Wall -Wextra -g -O0 -o main
```

- `-g` 加入调试信息；
- `-O0` 暂时关闭优化，使执行顺序更接近源代码，便于入门调试。

常见调试操作包括：

- 设置断点：运行到指定行或函数时暂停；
- 单步进入：进入被调用函数；
- 单步越过：执行当前行但不进入函数；
- 继续运行：到下一个断点；
- 查看变量：观察当前值；
- 查看调用栈：判断函数如何一层层调用到当前位置。

具体按钮或命令因 IDE、GDB、LLDB 等工具而异，但这些基本概念相同。

## 十四、调用栈能说明什么

程序崩溃时，当前行可能只是最后触发问题的位置。调用栈记录函数调用关系，例如：

```text
main
  -> load_students
      -> parse_record
          -> copy_name
```

如果崩溃发生在 `copy_name`，调用栈还能说明是哪次加载和解析把程序带到这里。递归错误、空指针来源和深层函数调用问题尤其需要查看调用栈。

## 十五、运行时检查工具

一些编译器提供运行时检测。GCC 和 Clang 常支持地址检查与未定义行为检查：

```text
gcc main.c -std=c11 -Wall -Wextra -g \
    -fsanitize=address,undefined -fno-omit-frame-pointer -o main
```

它们可能帮助发现：

- 数组和缓冲区越界；
- 释放后继续使用；
- 部分内存泄漏；
- 某些有符号溢出；
- 空指针或未对齐访问。

支持情况取决于编译器和平台。检测工具不能证明程序绝对正确，只能在实际执行到相关路径时报告可检测问题，所以仍需设计测试输入。

## 十六、边界测试

只测试“普通输入”无法覆盖许多错误。以数组处理函数为例，应考虑：

- 最小有效长度 1；
- 长度为 0；
- 最大允许长度；
- 全部元素相同；
- 全部为负数；
- 最大值位于第一个或最后一个位置；
- 输入格式错误；
- 文件为空或记录不完整。

边界通常是循环条件、数组下标、容量判断和除法分母最容易出错的地方。

## 十七、先写预期结果

测试前先明确预期：

```text
输入：80, 90, 100
总和：270
平均值：90.0
最大值：100
最小值：80
```

如果先运行再凭感觉判断输出“差不多”，容易忽略细小错误。预期结果应尽量可手工计算。

## 十八、修复后进行回归测试

修复一个输入案例后，还要重新运行此前通过的测试，确认修改没有破坏其他功能。这称为回归测试。

例如修复“空数组除零”后，还应重新测试：

- 单个元素；
- 多个正常元素；
- 最大容量；
- 文件加载后的数组。

每次新增功能都保留一组代表性测试，有助于避免旧问题再次出现。

## 十九、常见无效调试方式

### 1. 同时修改很多位置

无法知道哪个改动真正有效，也难以发现新增问题。

### 2. 只盯最终输出

最终错误可能由很早以前的状态污染造成，应寻找首次偏离。

### 3. 随机添加强制类型转换

这可能隐藏类型警告，却保留根本错误。

### 4. 忽略返回值

`scanf`、`fopen`、`fgets`、`malloc` 等失败后继续运行，后续症状会远离真正原因。

### 5. 依赖未初始化调试变量

调试输出本身也必须使用正确格式和有效数据，否则会制造新问题。

### 6. 认为不能复现就等于已经修复

不稳定问题可能来自未定义行为、未初始化数据或环境差异，需要记录条件并使用检查工具。

## 二十、一个完整调试案例

错误程序：

```c
double average(const int scores[], int count) {
    int sum;

    for (int i = 0; i <= count; i++) {
        sum += scores[i];
    }

    return sum / count;
}
```

逐项分析：

1. `sum` 没有初始化就参与加法；
2. 条件 `i <= count` 会访问 `scores[count]`，越过末尾；
3. `sum / count` 先执行整数除法，再转换为 `double`；
4. `count == 0` 时发生整数除零；
5. 没有检查 `scores` 是否为空。

修正：

```c
int average(const int scores[], int count, double *result) {
    if (scores == NULL || count <= 0 || result == NULL) {
        return 0;
    }

    long long sum = 0;

    for (int i = 0; i < count; i++) {
        sum += scores[i];
    }

    *result = (double)sum / count;
    return 1;
}
```

调试不是只修复第一个可见现象，而是检查函数输入约定、初始化、边界、类型转换和返回状态。

## 二十一、与相关知识的联系

- C01 编译流程：错误阶段决定应查看预处理器、编译器还是链接器信息。
- C14 输入输出：输入函数返回值和调试输出是重要证据来源。
- C35 动态内存：内存错误常需要运行时检查工具定位。
- C40 宏定义：宏展开可能改变真实表达式，查看预处理结果有助于调试。
- C42 文件读写：外部资源失败必须通过返回值、`perror` 和状态函数诊断。
- C44 未定义行为：看似随机或随优化变化的问题往往需要先排查未定义行为。

## 分层练习

1. 分别制造并识别一个编译错误和一个链接错误，记录关键诊断行。
2. 用调试输出逐轮观察求和循环，制作变量变化表。
3. 给数组平均值函数设计正常、单元素、空输入和最大容量测试。
4. 使用断点暂停在循环内部，观察下标、当前元素和累计值。
5. 使用编译器运行时检查选项测试一个越界示例，并根据报告定位源代码位置。

## 小结

调试是一套证据驱动的方法，而不是反复尝试。先确定错误阶段和稳定复现，再寻找程序状态首次偏离的位置。编译警告、返回值、调试输出、断言、调用栈和运行时检查工具各有用途；修复后还必须用边界与回归测试验证结果。
